# Corporate Tree Reconciliation Playbook

## Scope

Reconciles a client-provided corporate entity list against an Intapp party's Corporate Structure — covering the Tree, Shareholders, Beneficial Owners, Management/Board, and Close Affiliates. Identifies what already exists, what needs to be created, and what requires human judgement. Resolves ID conflicts before any matching. Checks parent chain integrity at the point of creation. Produces a full reconciliation report.

## Goals

- Minimise duplicate party creation by matching at a high name threshold before offering to create
- Use provided IDs as a safeguard and conflict alarm, not as a primary matching signal
- Ensure no entity is created without its direct parent being resolved first
- Produce a complete audit trail — every provided entity accounted for in the final report

## Playbook Variables

### Hardcoded

- `{threshold}` = `0.95` — minimum name similarity score for auto-accept. Applies to both entity name and parent name comparisons. Configurable per run.
- `{scoreSkill}` = `corp-tree-compare-score` — scoring skill (returns signals, `parent_provided`, `reconciliation`, and `reconciliation_note` per entity; classification is performed by the skill)

### Per-Run Variables

#### Party

- `{partyId}` — Intapp system ID of the anchor party
- `{partyName}` — display name of the anchor party
- `{provider}` — `externalDataProvider` value from the party response
- `{sourcesLoaded}` — list of non-null Corporate Structure sections found in the response

#### Entity Lists

- `{candidatePool}` — flat array of all existing nodes extracted in Step 1: `{ id, name, parentId, source }`
- `{providedList}` — parsed array of user-supplied entities: `{ name, id?, parentName?, parentId? }`
- `{idConflicts}` — pre-scoring: entities where provided ID exists in tree AND existing name ≠ provided name
- `{signalTable}` — output of `corp-tree-compare-score`: one row per provided entity containing signals, `parent_provided`, `reconciliation`, and `reconciliation_note` (after ID conflicts resolved)

#### Session State

- `{matches}` — rows from `{signalTable}` where `reconciliation` = `Match`
- `{noMatches}` — rows from `{signalTable}` where `reconciliation` = `No Match`
- `{judgements}` — rows from `{signalTable}` where `reconciliation` = `Judgement`
- `{outcomes}` — map of `providedName → { resolvedId, outcome, parentMatch, notes }` built throughout Phase 1

## Overall Behavior Rules

- **Silent computation:** All tool calls, signal scoring, candidate pool construction, and bucket classification produce zero user-facing output. Only defined display outputs and prompts are rendered.
- **No narration:** Never describe what you are about to do, what a tool call returned, or what computation just ran.
- **Exit checks are silent:** Exit checks are internal invariant assertions. If one fails, output only: `⚠️ Exit check failed: <reason>` and halt.
- **GO TO is unconditional:** When a step says GO TO Step N, proceed immediately — no confirmation, no summary.
- **Step labels are internal:** Never render step numbers or phase labels in user-facing output.

-----

## Execution Rules (Non-Negotiable)

- NEVER narrate tool calls, reasoning, data processing, or intermediate results
- NEVER explain what you are about to do or just did
- NEVER output any text between receiving tool results and the next defined step output
- The ONLY permitted outputs are: (a) Progress Header + Status, (b) defined display output, (c) defined user prompt
- NEVER render step or substep labels in output

### Step 3: Resolve ID Conflicts (bulk)

|Field                |Value                                                                                        |
|---------------------|---------------------------------------------------------------------------------------------|
|**Type**             |Display → User Prompt                                                                        |
|**Progress Header**  |`☑ **Find Tree**  ›  ▣ **Upload/Research**  ›  ☐ Reconcile  ›  ☐ Judgement Calls  ›  ☐ Report`|
|**Status**           |🔑 *We found {n} ID(s) in your list that exist in the tree with different names.*             |
|**Notification Rule**|Render conflict table then prompt                                                            |

This step is a pure ID-existence check. No name scoring runs here.

**Build `{idConflicts}`:** for every entity in `{providedList}` that has a provided ID:

- Look up the ID in `{candidatePool}`
- If found AND existing name == provided name (case-insensitive exact) → silently mark as Match in `{outcomes}`; do not surface
- If found AND names differ → add to `{idConflicts}`
- If not found → leave for scoring step (no ID assigned)

If `{idConflicts}` is empty → **GO TO** Step 4.

Render the conflict table:

| |ID          |Existing Name |New Name      |
|-|------------|--------------|--------------|
|A|{providedId}|{existingName}|{providedName}|
|B|…           |…             |…             |

Then prompt:

> │ Type **`A`** to keep existing names for all rows (resolve to existing tree nodes)

> │ Type **`B`** to rename existing tree nodes to match provided names

> │ Type **`C`** to add provided names as new entities (IDs dropped, sent to scoring)

> │ Type row-level decisions to resolve individually *(e.g., `1A, 2C, 3B`)*

On user decision:

- **A (all)** → for every conflict, resolve to existing tree node, record as Matched in `{outcomes}` with note "existing name preserved"
- **B (all)** → for every conflict, flag tree node for rename, record as Matched in `{outcomes}` with note "renamed: {existingName} → {providedName}". Then call `IntappJungle:editTree` with an `edit` mutation for each renamed node (see Appendix H). Batch all renames into a single call. After the editTree call completes: re-call `intappCommon:get_party`, rebuild `{candidatePool}`.
- **C (all)** → for every conflict, drop the provided ID from `{providedList}` (entity proceeds to scoring as a name-only entry). No outcome recorded yet — scoring will determine bucket.
- **Per-row decisions (e.g., "1A, 2C, 3B")** → apply mixed resolutions

**Exit check:** `{idConflicts}` is empty before proceeding.

### Step 4: Run Matching and Classification

|Field                |Value                                                                                        |
|---------------------|---------------------------------------------------------------------------------------------|
|**Type**             |Processing                                                                                   |
|**Progress Header**  |`☑ **Find Tree**  ›  ☑ **Upload/Research**  ›  ▣ **Reconcile**  ›  ☐ Judgement Calls  ›  ☐ Report`|
|**Status**           |⚙️ *Comparing provided information against corporate tree…*                                   |
|**Notification Rule**|No output except Progress Header + Status                                                    |

- Bootstrap `corp-tree-compare-score` (write score.py to disk if not already present — see skill SKILL.md)
- For each entity in `{providedList}` not already resolved in Step 3, run `corp-tree-compare-score` with `{candidatePool}` → collect one row per entity into `{signalTable}`
  - Pass `parentName` only if the provided entity has an explicit parent. For flat lists (no parent column), omit `parentName` entirely.
  - The skill returns `reconciliation` and `reconciliation_note` directly — no inline classification is required.
- Partition `{signalTable}` into `{matches}`, `{noMatches}`, `{judgements}` by reading the `reconciliation` field on each row.
- For `No Match` rows where `parent_provided = true`: use `strongest_parent_match_id` as the resolved add-under parent. The entity's own tree parent signal is disregarded for low entity matches.

**Exit check:** Every unresolved row in `{providedList}` has exactly one corresponding row in `{signalTable}`.

## Appendix A: Building the Candidate Pool

Flatten all non-null Corporate Structure sections from the `get_party` response into `{candidatePool}`:

**Tree nodes** — for each tree in `corporateTrees`, recurse `rootCompany.subCompanies`:

```
walk(node, parentId=null):
  append { id: node.externalId, name: node.name, parentId: parentId, source: "Tree" }
  for each child in node.subCompanies: walk(child, node.externalId)
```

Skip duplicate `externalId` values across trees (first occurrence wins).

**Shareholders** — `shareholders.shareholders[]` → `{ id, name, parentId: "", source: "Shareholder" }`

**Beneficial Owners** — `beneficialOwners.beneficialOwners[]`, recurse nested `beneficialOwners`:

```
walkUBO(ubo, parentId=""):
  append { id: ubo.id, name: ubo.name, parentId: parentId, source: "Beneficial Owner" }
  for each child in ubo.beneficialOwners: walkUBO(child, ubo.id)
```

**Management/Board** — `boardMembers.boardMembers[]` → `{ id, name, parentId: "", source: "Management/Board" }`

**Close Affiliates** — `closeAffiliates.closeAffiliates[]` → `{ id, name, parentId: "", source: "Close Affiliate" }`

Skip any section that is null.

## Appendix C: Bucket Partitioning Rules

Classification is performed by the `corp-tree-compare-score` skill. Each row in `{signalTable}` includes a `reconciliation` field (`Match` / `Judgement` / `No Match`) and a `reconciliation_note` describing the basis for the classification.

### Partition

**`{matches}`** — rows where `reconciliation` = `Match`

**`{noMatches}`** — rows where `reconciliation` = `No Match`

**`{judgements}`** — rows where `reconciliation` = `Judgement`

### reconciliation_note reference

| Note | Condition |
|---|---|
| `Strong entity match. No parent provided.` | entity ≥ 95%, flat list |
| `Moderate entity match. No parent provided.` | 60–94%, flat list |
| `Low entity match. No parent provided.` | < 60%, flat list |
| `Strong entity match. Strong parent match.` | entity ≥ 95%, parent agrees |
| `Strong entity match. Discrepancy parent match.` | entity ≥ 95%, parent strong but points to different node |
| `Strong entity match. Low parent match.` | entity ≥ 95%, parent weak or not found |
| `Moderate entity match. Strong parent match.` | 60–94%, parent agrees |
| `Moderate entity match. Discrepancy parent match.` | 60–94%, parent strong but points to different node |
| `Moderate entity match. Low parent match.` | 60–94%, parent weak or not found |
| `Low entity match.` | < 60%, parent provided — add under `strongest_parent_match_id` |
| `No candidates in pool.` | candidate pool is empty |

### parent_agrees logic (for reference only — evaluated inside the skill)

```
parent_agrees = (entity_match_parent_id is not None AND entity_match_parent_id == strongest_parent_match_id) OR (entity_match_parent_id_score is not None AND entity_match_parent_id_score >= threshold)
```

If both conditions are unevaluable (both null), `parent_agrees = false`.

Note: ID conflicts are resolved in Step 3 before scoring runs. Any entity surviving Step 3 with a resolved ID and matching name is already recorded as Matched in `{outcomes}` and excluded from scoring input.

## Appendix D: Immediate Parent Check

Triggered before every node add during Steps 6 and 7.

1. Does the provided parent name/ID exist in `{candidatePool}`? → proceed
2. Has the provided parent already been created this session (in `{outcomes}`)? → proceed
3. Parent not found anywhere → halt and surface:

```
⚠ Before creating [{entityName}], its parent needs to be resolved:
   Parent: {parentName} — not found in tree and not yet created.

   → Add [{parentName}] first | Skip (blocks [{entityName}] and all its children)
```

If the parent needs to be created, apply this check recursively to the parent before creating it. Stop as soon as a node that exists is found. If user skips any ancestor → mark that ancestor and all descendants as `Skipped — ancestor not resolved` in `{outcomes}`. Do not create anything below a skipped node.

All creation actions in this check use `IntappJungle:editTree` (Appendix E), not `intappCommon:create_party`.

## Appendix E: Adding Nodes to the Corporate Tree

Use `IntappJungle:editTree` to add new entities directly to the corporate tree. Do **not** call `intappCommon:create_party` — tree placement via `editTree` is the only required action.

### Tool parameters

| Parameter | Value |
|---|---|
| `providerType` | The tree's provider type. Read from `corporateTrees[0].providerType` on the party response. Common values: `Internal`, `DunAndBradstreet`, `BureauVanDijk`, `SPGlobal`. Example: a manually-maintained tree uses `Internal`. |
| `rootId` | The `externalId` of the tree root node (e.g. `042006515` for Innospec Inc.). |
| `add` | Array of nodes to add — see schema below. |

### Node schema

```json
{
  "id": "custom-{slugified-entity-name}",
  "idParent": "{externalId of parent node}",
  "name": "{entityName}"
}
```

**ID convention for new nodes:** Use `custom-` prefix followed by a lowercase hyphenated slug of the entity name (e.g. `custom-innospec-deutschland-gmbh`). This distinguishes manually-added nodes from provider-assigned IDs.

### Batching

Multiple nodes can be added in a single `editTree` call via the `add` array. Batch all nodes being added in the same step into one call rather than making sequential calls.

### Example

Adding two new subsidiaries under Innospec Inc. (root `042006515`) on an internally-maintained tree:

```json
{
  "providerType": "Internal",
  "rootId": "042006515",
  "add": [
    {
      "id": "custom-innospec-deutschland-gmbh",
      "idParent": "042006515",
      "name": "Innospec Deutschland GmbH"
    },
    {
      "id": "custom-chemtec-chemical-co",
      "idParent": "042006515",
      "name": "Chemtec Chemical Co."
    }
  ]
}
```

### After the call

- Record the `id` used as `resolvedId` in `{outcomes}` for each added node.
- For person entities (board members, UBOs) — if the tree does not accommodate person nodes, skip tree placement and note as `Unresolved — person entity, tree placement not applicable`.
- If party type is uncertain, skip and surface for manual review rather than guessing.


|Score     |iconAft|iconAftSuffix  |
|----------|-------|---------------|
|≥95%      |🟢     |`{score}%`     |

### Step 1 — Collect all matched nodes across all options

For the current judgement call, identify every node that is relevant to any option:

- **Option A entity match** — the best existing candidate match for the provided entity name (`{topNameMatchId}`)
- **Option A direct parent** — the tree parent of that matched entity (`{treeParentId}`)
- **Option B direct parent** — the best existing candidate match for the provided parent name (`{resolvedParentId}`), if a parent was provided; otherwise the tree root

For each of these nodes, walk up `{candidatePool}` via `parentId` links until `parentId` is null (ultimate owner). Collect every ancestor along the way.

The union of all these nodes — matched nodes, their direct parents, and all ancestors up to root — forms the **shared skeleton**.

Deduplicate by `id`. Preserve `parentId` links from `{candidatePool}` so the tree renders correctly.

---

### Step 2 — Annotate per option

For each option, start with the shared skeleton and apply icons only to nodes relevant to that option. All other nodes in the skeleton render with `iconAft: null` and `iconAftSuffix: null`.

**Score field reference — use exactly these fields, never substitute one for the other:**

| Option | Scored node | Score field from `corp-tree-compare-score` output |
|---|---|---|
| A | `{treeParentId}` (`strongest_entity_match_parent_id`) | `strongest_entity_match_parent_id_score` — similarity of provided parent name against the matched entity's *actual tree parent* |
| B | `{resolvedParentId}` (`strongest_parent_match_id`) | `strongest_parent_match_score` — similarity of provided parent name against the best pool candidate for that parent |

These two fields measure different comparisons and will often differ. Never use `strongest_parent_match_score` for Option A or `strongest_entity_match_parent_id_score` for Option B.

#### Option A — Match existing entity

| Node | iconAft | iconAftSuffix |
|---|---|---|
| `{treeParentId}` (direct parent of matched entity) | icon for `strongest_entity_match_parent_id_score` | `{strongest_entity_match_parent_id_score * 100}%` — only if a parent was provided in input; otherwise `null`/`null` |
| `{topNameMatchId}` (matched entity) | icon for `strongest_entity_match_score` | `{strongest_entity_match_score * 100}%` |
| All other skeleton nodes | `null` | `null` |

The new entity is **not** inserted — Option A matches an existing node.

#### Option B — Add new entity

| Node | iconAft | iconAftSuffix |
|---|---|---|
| `{resolvedParentId}` (provided parent match) | icon for `strongest_parent_match_score` | `{strongest_parent_match_score * 100}%` |


## Appendix H: editTree — Corporate Tree Mutation

Use `IntappJungle:editTree` to rename or delete nodes in a corporate tree. For adding new nodes, see Appendix E.

### Required Parameters

| Parameter | Value |
|---|---|
| `rootId` | External ID of the root company (e.g. DUNS `042006515`). Always the tree root — not an Intapp party ID. |
| `providerType` | One of: `DunAndBradstreet` \| `BureauVanDijk` \| `SPGlobal` |

### Optional Mutation Arrays

Omit any array that has no operations. Both may be included in a single call.

| Array | Operation | Required fields |
|---|---|---|
| `edit` | Rename existing nodes by external ID | `id`, `name` |
| `delete` | Remove a node and its entire subtree | `id` |

**Execution order within a single call:** deletions run first, then edits.

### Determining rootId and providerType

1. Inspect `{candidatePool}` for the anchor party's primary tree root (the node with `parentId = null` in the Tree source).
2. The root node's `id` field is its `externalId` — use this as `rootId`.
3. `providerType` is derived from `{provider}` (the `externalDataProvider` field from the `get_party` response):

| externalDataProvider | providerType |
|---|---|
| `DunBradstreet` | `DunAndBradstreet` |
| `BureauVanDijk` | `BureauVanDijk` |
| `SPGlobal` | `SPGlobal` |
| `None` or blank | Use `DunAndBradstreet` as default; note in outcomes |

If the party has multiple trees, always target the primary tree (first entry in `corporateTrees`).

### Example — Rename a Node

```json
{
  "rootId": "042006515",
  "providerType": "DunAndBradstreet",
  "edit": [
    { "id": "042006516", "name": "Innospec Active Chemicals LLC (Renamed)" }
  ]
}
```

### Error Handling

If `editTree` returns an error:

- Record the failure in `{outcomes}` with a note of `rename/delete failed — {error message}`.
- Do not halt the playbook. Continue to the next entity.
- Surface a warning in the Step COMPLETE report header:

```
⚠ {n} tree mutation(s) failed — see Notes column.
```

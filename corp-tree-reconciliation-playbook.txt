# Corporate Tree Reconciliation Playbook

## Scope

Reconciles a client-provided corporate entity list against an Intapp party's Corporate Structure — covering the Tree, Shareholders, Beneficial Owners, Management/Board, and Close Affiliates. Identifies what already exists, what needs to be created, and what requires human judgement. Resolves ID conflicts before any matching. Checks parent chain integrity at the point of creation. Produces a full reconciliation report.

## Goals

- Minimise duplicate party creation by matching at a high name threshold before offering to create
- Use provided IDs as a safeguard and conflict alarm, not as a primary matching signal
- Ensure no entity is created without its direct parent being resolved first
- Produce a complete audit trail — every provided entity accounted for in the final report

## Playbook Variables

### Hardcoded

- `{threshold}` = `0.95` — minimum name similarity score for auto-accept. Applies to both entity name and parent name comparisons. Configurable per run.
- `{matchSkill}` = `corp-tree-match` — scoring skill
- `{interpretSkill}` = `corp-tree-interpret` — classification skill

### Per-Run Variables

#### Party

- `{partyId}` — Intapp system ID of the anchor party
- `{partyName}` — display name of the anchor party
- `{provider}` — `externalDataProvider` value from the party response
- `{sourcesLoaded}` — list of non-null Corporate Structure sections found in the response

#### Entity Lists

- `{candidatePool}` — flat array of all existing nodes extracted in Step 1: `{ id, name, parentId, source }`
- `{providedList}` — parsed array of user-supplied entities: `{ name, id?, parentName?, parentId? }`
- `{idConflicts}` — pre-scoring: entities where provided ID exists in tree AND existing name ≠ provided name
- `{signalTable}` — output of `corp-tree-match`: one signal row per provided entity (after ID conflicts resolved)
- `{bucketTable}` — output of `corp-tree-interpret`: signal rows + Bucket + Interpretation columns

#### Session State

- `{matches}` — rows with Bucket = Match
- `{noMatches}` — rows with Bucket = No Match
- `{judgements}` — rows with Bucket = Judgement
- `{outcomes}` — map of `providedName → { resolvedId, treeNodeId?, outcome, parentMatch, notes }` built throughout Phase 1. `treeNodeId` is set for Created entities and holds the `INTAPP-{partyId}` string used as the node's external ID in the corporate tree.

-----

## Overall Behavior Rules

- **Silent computation:** All tool calls, signal scoring, candidate pool construction, and bucket classification produce zero user-facing output. Only defined display outputs and prompts are rendered.
- **No narration:** Never describe what you are about to do, what a tool call returned, or what computation just ran.
- **Exit checks are silent:** Exit checks are internal invariant assertions. If one fails, output only: `⚠️ Exit check failed: <reason>` and halt.
- **GO TO is unconditional:** When a step says GO TO Step N, proceed immediately — no confirmation, no summary.
- **Step labels are internal:** Never render step numbers or phase labels in user-facing output.

-----

## Execution Rules (Non-Negotiable)

- NEVER narrate tool calls, reasoning, data processing, or intermediate results
- NEVER explain what you are about to do or just did
- NEVER output any text between receiving tool results and the next defined step output
- The ONLY permitted outputs are: (a) Progress Header + Status, (b) defined display output, (c) defined user prompt
- NEVER render step or substep labels in output

### Research Step 2: Fetch and Parse Sources

|Field                |Value                                                                                    |
|---------------------|-----------------------------------------------------------------------------------------|
|**Type**             |Processing                                                                               |
|**Progress Header**  |`▣ **Fetch & Parse**  ›  ☐ ID Conflicts  ›  ☐ Match & Score  ›  ☐ Reconcile  ›  ☐ Report`|
|**Status**           |🔍 *Fetching {n} source(s)…*                                                              |
|**Notification Rule**|No output except Progress Header + Status                                                |

For each selected source:

- Fetch the document and extract all entity names, jurisdictions, and any available parent or relationship information.
- Detect the structure: explicit hierarchy, flat list with parent column, flat list only.
- If explicit hierarchy or parent column → extract `{ name, parentName }` pairs.
- If flat list only → set `parentName` = name of the registrant (party GUO or root) with note "assumed direct subsidiary — source provides no hierarchy".
- If structure is ambiguous (e.g. visual groupings, indented formatting without explicit labels) → treat as flat list. Do not infer hierarchy from visual layout.
- Tag each entity with `{ source, confidence, filingDate?, assumedParent: true/false }`.

Set `{researchRaw}` — all extracted entities before deduplication.

### Research Step 3: Merge and Deduplicate

|Field                |Value                                                                                    |
|---------------------|-----------------------------------------------------------------------------------------|
|**Type**             |Processing                                                                               |
|**Progress Header**  |`▣ **Fetch & Parse**  ›  ☐ ID Conflicts  ›  ☐ Match & Score  ›  ☐ Reconcile  ›  ☐ Report`|
|**Status**           |🔍 *Merging sources…*                                                                     |
|**Notification Rule**|No output except Progress Header + Status                                                |

Merge `{researchRaw}` into a single deduplicated list:

- Normalize all names (apply client stopwords if available; otherwise strip standard legal suffixes).
- For each entity, find any existing entry in the merged list with normalized name similarity ≥ 99%.
- **Match found:** merge sources into a combined `sources` array. If parent info conflicts across sources, retain the higher-confidence source's parent and note the conflict.
- **No match:** add as new entry.
- **Short normalized name (≤ 6 characters after stripping):** do not auto-merge — flag for manual review. Short names are high risk for false merges.

Set `{researchMerged}` — deduplicated list with `{ name, parentName, sources[], confidence, assumedParent, notes? }`.

### Step 3: Resolve ID Conflicts (bulk)

|Field                |Value                                                                                        |
|---------------------|---------------------------------------------------------------------------------------------|
|**Type**             |Display → User Prompt                                                                        |
|**Progress Header**  |`☑ **Fetch & Parse**  ›  ▣ **ID Conflicts**  ›  ☐ Match & Score  ›  ☐ Reconcile  ›  ☐ Report`|
|**Status**           |🔑 *We found {n} ID(s) in your list that exist in the tree with different names.*             |
|**Notification Rule**|Render conflict table then prompt                                                            |

This step is a pure ID-existence check. No name scoring runs here.

**Build `{idConflicts}`:** for every entity in `{providedList}` that has a provided ID:

- Look up the ID in `{candidatePool}`
- If found AND existing name == provided name (case-insensitive exact) → silently mark as Match in `{outcomes}`; do not surface
- If found AND names differ → add to `{idConflicts}`
- If not found → leave for scoring step (no ID assigned)

If `{idConflicts}` is empty → **GO TO** Step 4.

Render the conflict table:

| |ID          |Existing Name |New Name      |
|-|------------|--------------|--------------|
|A|{providedId}|{existingName}|{providedName}|
|B|…           |…             |…             |

Then prompt:

> │ Type **`A`** to keep existing names for all rows (resolve to existing tree nodes)

> │ Type **`B`** to rename existing tree nodes to match provided names

> │ Type **`C`** to add provided names as new entities (IDs dropped, sent to scoring)

> │ Type row-level decisions to resolve individually *(e.g., `1A, 2C, 3B`)*

On user decision:

- **A (all)** → for every conflict, resolve to existing tree node, record as Matched in `{outcomes}` with note "existing name preserved"
- **B (all)** → for every conflict, flag tree node for rename, record as Matched in `{outcomes}` with note "renamed: {existingName} → {providedName}". Then call `IntappJungle:editTree` with an `edit` mutation for each renamed node (see Appendix H). Batch all renames into a single call. After the editTree call completes: re-call `intappCommon:get_party`, rebuild `{candidatePool}`.
- **C (all)** → for every conflict, drop the provided ID from `{providedList}` (entity proceeds to scoring as a name-only entry). No outcome recorded yet — scoring will determine bucket.
- **Per-row decisions (e.g., "1A, 2C, 3B")** → apply mixed resolutions

**Exit check:** `{idConflicts}` is empty before proceeding.

### Step 7: Judgement Calls (one at a time)

|Field                |Value                                                                                            |
|---------------------|-------------------------------------------------------------------------------------------------|
|**Type**             |Display → User Prompt                                                                            |
|**Progress Header**  |`☑ **Fetch & Parse**  ›  ☑ **ID Conflicts**  ›  ☑ **Match & Score**  ›  ▣ **Reconcile**  ›  ☐ Report`|
|**Status**           |✏️ *Judgement Call {i} of {n}*                                                                    |
|**Notification Rule**|One prompt card per entity; render next only after current is resolved                           |

If `{judgements}` is empty → **GO TO** Step COMPLETE.

**Unresolved parent check:** Before rendering the card, check whether the entity's provided parent has outcome `Unresolved` in `{outcomes}`. If so, render:

> ⚠ **[{providedParentName}]** was skipped and has not been added to the tree.
> → Type **`ADD`** to create it now (before this entity) | Type **`SKIP`** to skip this entity

- **ADD** → run the immediate parent check (Appendix D), call `intappCommon:create_party` for the parent, record as Created in `{outcomes}`, then continue to render the judgement card normally.
- **SKIP** → record entity as `Unresolved — parent not resolved` in `{outcomes}` and advance to the next judgement card without rendering it.

If the entity has no provided parent, or the provided parent is not present in `{outcomes}` at all, skip this check.

For each entity in `{judgements}`, render the card header table:

|      |Provided Name       |Best Existing Match                  |Match Score   |
|------|--------------------|-------------------------------------|--------------|
|Entity|{providedName}      |{topNameMatch} ({topNameMatchId})    |{entityScore}%|
|Parent|{providedParentName}|{topParentMatch} ({topParentMatchId})|{parentScore}%|

If no parent was provided, the Parent row shows `—` in Provided Name, `—` in Best Existing Match, and `—` in Match Score.

Then render the curated options for the matching variant below. For each option, render the option label followed immediately by a `chat-tree-display` tree showing the result. Build the nodes payload per **Appendix F**, then render using the `chat-tree-display` skill.

For Option A, the parent node always shows the matched entity's actual existing tree parent (`{treeParentId}`, `{treeParentName}`). Show `iconAft` and `iconAftSuffix` (match score against provided parent) on the parent node only if a parent was provided in the input. If no parent was provided, set `iconAft: null` and `iconAftSuffix: null` on the parent node.

**Moderate name match (entity score < threshold), parent corroborates:**

**Option A** — Match Existing Entity (Moderate Match) under Existing Parent (Strong Match)
**Option B** — Add New Entity under Existing Parent (Strong Match)

> │ Type **`A`**, **`B`** or **`SKIP`**

**Strong name match (entity score ≥ threshold), parent not found or fuzzy:**

**Option A** — Match Existing Entity (Strong Match) under Existing Parent (keep tree placement)
**Option B** — Add New Entity under Provided Parent ({parentQuality})

> │ Type **`A`**, **`B`** or **`SKIP`**

**Strong name and parent matches, but relationship doesn't exist in tree:**

**Option A** — Match Existing Entity (Strong Match) under Existing Parent ({existingParentQuality})
**Option B** — Add New Entity under Provided Parent (Strong Match)

## Appendix A: Building the Candidate Pool

Flatten all non-null Corporate Structure sections from the `get_party` response into `{candidatePool}`:

**Tree nodes** — for each tree in `corporateTrees`, recurse `rootCompany.subCompanies`:

```
walk(node, parentId=null):
  append { id: node.externalId, name: node.name, parentId: parentId, source: "Tree" }
  for each child in node.subCompanies: walk(child, node.externalId)
```

Skip duplicate `externalId` values across trees (first occurrence wins).

**Shareholders** — `shareholders.shareholders[]` → `{ id, name, parentId: "", source: "Shareholder" }`

**Beneficial Owners** — `beneficialOwners.beneficialOwners[]`, recurse nested `beneficialOwners`:

```
walkUBO(ubo, parentId=""):
  append { id: ubo.id, name: ubo.name, parentId: parentId, source: "Beneficial Owner" }
  for each child in ubo.beneficialOwners: walkUBO(child, ubo.id)
```

**Management/Board** — `boardMembers.boardMembers[]` → `{ id, name, parentId: "", source: "Management/Board" }`

**Close Affiliates** — `closeAffiliates.closeAffiliates[]` → `{ id, name, parentId: "", source: "Close Affiliate" }`

Skip any section that is null.

## Appendix H: editTree — Corporate Tree Mutation

Use `IntappJungle:editTree` to insert, rename, or delete nodes in a corporate tree after a party has been created via `create_party`.

### Required Parameters

| Parameter | Value |
|---|---|
| `rootId` | External ID of the root company (e.g. DUNS `042006515`). Always the tree root — not an Intapp party ID. |
| `providerType` | One of: `DunAndBradstreet` \| `BureauVanDijk` \| `SPGlobal` |

### Optional Mutation Arrays

Omit any array that has no operations. All three may be included in a single call.

| Array | Operation | Required fields |
|---|---|---|
| `add` | Insert new nodes | `id`, `idParent`, `name` |
| `edit` | Rename existing nodes by external ID | `id`, `name` |
| `delete` | Remove a node and its entire subtree | `id` |

**Execution order within a single call:** deletions run first, then edits, then additions.

### ID Conventions for New Nodes

New nodes added via `create_party` have no provider external ID. Use the pattern `INTAPP-{partyId}` as the node's `id` in `editTree`, where `{partyId}` is the integer ID returned by `create_party`.

Store this generated ID as `treeNodeId` in `{outcomes}` alongside `resolvedId`.

### Determining rootId and providerType

1. Inspect `{candidatePool}` for the anchor party's primary tree root (the node with `parentId = null` in the Tree source).
2. The root node's `id` field is its `externalId` — use this as `rootId`.
3. `providerType` is derived from `{provider}` (the `externalDataProvider` field from the `get_party` response):

| externalDataProvider | providerType |
|---|---|
| `DunBradstreet` | `DunAndBradstreet` |
| `BureauVanDijk` | `BureauVanDijk` |
| `SPGlobal` | `SPGlobal` |
| `None` or blank | Use `DunAndBradstreet` as default; note in outcomes |

If the party has multiple trees, always target the primary tree (first entry in `corporateTrees`).

### Batching Rule

All nodes being added in a single step (Step 6 ADD ALL, or multiple parents + children in Step 7) MUST be submitted in a single `editTree` call, not one call per node. The `add` array supports forward references: a node can reference another node in the same `add` array as its `idParent` — ordering is handled automatically.

### Example — Add Two Nodes

```json
{
  "rootId": "042006515",
  "providerType": "DunAndBradstreet",
  "add": [
    { "id": "INTAPP-9001", "idParent": "042006515", "name": "NewCo Oilfield Services Ltd" },
    { "id": "INTAPP-9002", "idParent": "INTAPP-9001", "name": "NewCo Sub LLC" }
  ]
}
```

### Example — Rename a Node

```json
{
  "rootId": "042006515",
  "providerType": "DunAndBradstreet",
  "edit": [
    { "id": "042006516", "name": "Innospec Active Chemicals LLC (Renamed)" }
  ]
}
```

### Error Handling

If `editTree` returns an error:

- Record the failure in `{outcomes}` as `Created — tree insert failed` with the error message in Notes.
- Do not halt the playbook. Continue to the next entity.
- Surface a warning in the Step COMPLETE report header:

```
⚠ {n} tree insert(s) failed — parties were created but not linked in the tree. See Notes column.
```
